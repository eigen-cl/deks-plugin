# DEKS OpenAI candidate 1.0.2

This candidate is prepared in a separate public-upload tree. The submitted 1.0.1
archive, all version-labelled 0.4.2 evidence, shared skills and private bindings
remain unchanged. A build is preparation, not deployment, portal upload, review
submission or approval.

## Acceptance scenarios

- Given the current submitted skill archive and frozen source hashes, when this
  candidate is prepared, all protected files still match their recorded hashes.
- Given a portable upload, when validated, it contains one plugin root with root
  plugin.json, mcp.json, exactly four Cloud skills and the actual DEKS PNG icon.
  No app binding, compatibility manifest, credentials, private file, symlink,
  traversal path or unrelated file may enter the archive.
- Given the remediation contract, every tool declares four boolean annotations;
  there are 37 descriptors and 36 model-visible tools, with a private deletion
  executor and the v5 confirmation UI. The generic batch entry point is absent.
- Given five positive and three negative independent review cases, their prompts
  express natural user goals; exact tool and argument expectations belong in the
  expected behavior. Every expected tool belongs to the new contract.
- Given fixed source bytes, two package builds are byte-identical. Validation
  checks the archive bytes against source, not only the unpackaged manifest.
- Given an unverified demo or unrun live case, package validation reports that
  readiness gap. It never fabricates a demo URL, a passed result or reviewer access.

The new metadata is only usable after the API remediation is deployed and its
live discovery matches the copied source contract. Source tests do not prove that
the old live 1.0.1 endpoint already implements this candidate.
